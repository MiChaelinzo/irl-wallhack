# 09 Rendering and compute optimisation

All numbers are from `docs/perf-rf.md`, generated by `python tools/perf_rf_browser.py` (FEAT-005). Machine: Intel Xeon Platinum 8488C, 8 logical cores, node v22.23.4, headless Chromium 159 on SwiftShader, not a Raspberry Pi 4 and not a user's laptop. UNVERIFIED on a Pi 4 and on a real GPU.

## Measured: 100,489 points

Scenario: 100 m x 100 m floor, 1000 walls (seed 7), 4 APs, 2.4 GHz, basic mode, 6 runs with a warm-up, medians.

| Worker, first usable frame, Chromium | 146.7 |

## Decisions

| Option | Decision | Reason (measured or structural) |
|---|---|---|
| Quadtree for walls | Not adopted | 990 ms vs 398 ms for the grid on the same kernel. Walls are short and evenly spread, a uniform grid wins. |
| Octree | Not applicable | The engine is 2D with a fixed loss per floor. An octree needs 3D geometry. Revisit with true 3D propagation. |
| GPU compute (WebGPU or WebGL) | Not built, design only | No measurement supports a need yet. The WebGL path in `planner-heat.js` only draws the grid, it does not compute it. |
| Progressive rendering | Already exists | `rf-worker.js` sends a coarse frame first, then tiles; `planner.js` `setGrid` shows them. No duplicate was added. |
| Per-AP tile cache | Already exists | Wall edit recomputed 8 of 104 tiles (25.8 ms median final in the 1 AP, 0.5 m case). |

## Open performance finding

The engine grid path (1675 ms) is about 4x slower than the same-algorithm bench kernel (398 ms), and both produce identical values. The cause is not profiled. A hypothesis, unverified: candidate sorting and closure allocation per cell in `segmentCandidates` and `wallLoss` (`rf-engine.js`). Next step: profile with `node --cpu-prof tools/perf_rf.js --points 100000` before changing anything. A 4x gain would bring a 100k grid near 0.5 s without any new data structure.

## Rendering path

| Layer | Technique | File |
|---|---|---|
| Heat map | RSSI grid as 8-bit texture, colour LUT in a fragment shader, canvas fallback chosen when WebGL is missing or fails | `wallhack/static/planner-heat.js` |
| Contours, legend, minimap | canvas 2D | `planner-heat.js` |
| Editor | canvas 2D, three stacked canvases plus an edit canvas | `planner-editor.js` |
| 3D | hand-written projection on a 2D canvas | `view3d.js` |

Page-level frame timing in headless Chromium is in `docs/perf-rf.md` "Planner page". It ran on SwiftShader (software), so it does not show real GPU performance (UNVERIFIED).

## Recommendations

1. Profile and fix the engine grid path (see above).
2. Measure on a Raspberry Pi 4 before promising anything about that device.
3. Keep the coarse-first strategy: it gives a first picture in about 145 ms at 100k points regardless of the final cost.
