# RF planner performance (measured)

Generated by `python tools/perf_rf_browser.py` on 2026-11-21. Every number below was measured in that run. Run it again on your own hardware: these are not Raspberry Pi 4 numbers.

## Machine

Intel(R) Xeon(R) Platinum 8488C, 8 logical cores, Linux-6.1.190-237.442.amzn2023.x86_64-x86_64-with-glibc2.34, Python 3.11.15, node v22.23.4, Chromium 159.0.8154.6 (headless, Playwright)

## Method

- Test floor: seeded (`tools/perf_rf_lib.js`, seed 7) 100 m x 60 m, 1000 axis-aligned walls of 2 to 8 m with mixed materials, 1, 4 or 8 access points at 20 dBm, 2.4 GHz, basic propagation mode.
- Each case is run 5 times after one warm-up run; the table shows median, min and max in milliseconds. Times run from the `compute` message until the first message (the coarse pass, the first picture the user sees) and until the final result.
- Cold cases reload the project before each run, so no tile is cached. AP move and wall edit cases change one thing and recompute with the per-AP tile cache warm.
- Node rows run the worker core (`rf-worker.js`) in a node process. Browser rows run the same code in a real Web Worker inside headless Chromium, started from the live /planner page.
- Page rows load the 4 AP stress floor into the real planner page and time `benchmarkRender` (full frames: base layer, heat map, contours, editor layer, mini-map), and a scripted AP drag of 90 steps (one `store.exec` per animation frame) while recording `requestAnimationFrame` intervals.
- Index versus brute force uses the same engine with and without the uniform grid index (`brute: true`).

## WebGL in this run

- WebGL path in headless Chromium: **RAN (WebGL context created)**. Renderer string reported by the browser: `ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero) (0x0000C0DE)), SwiftShader driver)`.
- Frame intervals are bounded by this environment: the idle baseline column shows the same page with nothing happening, so compare the drag column with it, not with 16.7 ms. Headless Chromium composites the page's blur and glass effects in software.
- A software GL implementation (SwiftShader) is not a GPU. The WebGL frame times above say nothing about GPU speed, only that the shader path works and is correct enough to draw.
- The canvas 2D row was forced with `?renderer=canvas2d`, the main-thread row with `?worker=0`.

## Reading the numbers

- Target from the plan: coarse pass under 250 ms for 4 APs and 1000 walls. Measured median 33 ms (max 35.4 ms): met.
- Full refinement is not interactive for many APs: 4 APs at 0.5 m take 572.2 ms and 8 APs take 1123.4 ms from a cold cache. The picture appears after the coarse pass and sharpens tile by tile.
- Moving one AP recomputes only that AP, so the cost does not grow with the number of other APs (see the AP move rows).
- A wall edit recomputes a tile only when the box spanned by the AP and the tile meets the wall's box. That test is conservative: for 8 APs the median final time is 278.6 ms (max 561.7 ms) because wall edits near the middle of the floor meet many long boxes. Enhanced and multipath modes recompute everything on any wall edit.
- The uniform wall index helps less than expected with this floor: brute force was 1.1x slower than the index at 0.5 m. `rayWallHit` rejects most walls with a cheap bounding box test, so brute force is cheap per cell. The index matters more as walls per ray grow.
- Idle frame intervals of the same page differ between runs (compositing in software), so frame interval comparisons between rows are rough. The long task count is the more reliable smoothness signal: no task over 50 ms blocked the main thread while dragging with the Web Worker.
- The main-thread fallback (no Worker) keeps working but its drag frame interval is longer, as expected from computing in 8 ms slices on the UI thread.
