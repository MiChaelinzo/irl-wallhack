# Contributing

Short guide for working on irl-wallhack. Project rules: Python is the reference for every RF number, the browser engine mirrors it, every constant lives in one config file, results are deterministic, and anything not measured is labelled as an estimate or UNVERIFIED.

## Setup

Needs Python 3.9 or newer and Node 18 or newer (Node is only used by tests and syntax checks).

```
./install.sh                                              # creates .venv
.venv/bin/python -m pip install -r requirements-dev.txt   # pytest and httpx
.venv/bin/python -m wallhack --source simulator           # dashboard at 127.0.0.1:8000, planner at /planner
```

There is no JavaScript build step and no `node_modules`. The front end is vanilla JavaScript with JSDoc ([ADR](docs/platform/adr-frontend-stack.md)).

## Checks to run before a commit

```
.venv/bin/python -m pytest -q
for f in wallhack/static/*.js; do node --check "$f"; done
bash -n scripts/pi_setup.sh install.sh run.sh
.venv/bin/python tools/build_demo.py && test -s dist/index.html && test -s dist/recording.json
```

CI runs the same four steps on Python 3.9 and 3.12. Browser checks need `pip install playwright && playwright install chromium`:

```
PLAYWRIGHT_NODEJS_PATH=$(which node) .venv/bin/python tools/planner_smoke.py [--demo]
PLAYWRIGHT_NODEJS_PATH=$(which node) .venv/bin/python tools/screenshot.py [--demo]
.venv/bin/python tools/a11y_check.py          # axe-core, fetched from npm at run time, never committed
```

Run the smoke tool when you change anything under `wallhack/static/planner*.js` or `planner.html`. Screenshots in `docs/` are regenerated by these tools, not edited by hand.

## Where things live

| Concern | File |
|---|---|
| Reference RF model (source of truth) | `wallhack/rfmodel.py` |
| Browser mirror | `wallhack/static/rf-engine.js` |
| Every RF constant, with sources | `wallhack/static/rf-config.json`, schema `rf-config.schema.json` |
| Building model validation | `wallhack/twin.py` (Python) and `wallhack/static/planner-state.js` (JavaScript) |
| Planning heuristics | `wallhack/static/rf-optimizer.js` |
| Architecture diagram | `docs/platform/03-architecture.md` |

## Parity workflow (changing a propagation rule)

1. Change `wallhack/rfmodel.py` and add or update its test in `tests/test_rfmodel.py`, `tests/test_wifi_standards.py` or `tests/test_rf_lab.py`. Prefer a hand-computed expected value over a snapshot.
2. Put any new number in `rf-config.json` (with a `source` or an assumption note) and update `rf-config.schema.json`. No magic numbers in code.
3. Mirror the change in `rf-engine.js`. Keep operation order the same, because sums are compared within 0.1 dB.
4. Run `tests/test_rf_parity.py` and the lab and standards tests. They run the JS engine under node and compare it with Python.
5. Legacy projects must keep producing identical output: `tests/fixtures/rf_legacy_golden.json` must not change unless the change is a deliberate fix. Say so in the CHANGELOG.
6. Update `docs/rf-planner.md`, `docs/platform/15-wifi-physics.md`, the README verification table and the CHANGELOG. Mark what is VERIFIED, PARTIALLY VERIFIED and UNVERIFIED honestly.

Randomness must be seeded. The same input must give the same output.

## Adding a material

1. Add an entry under `materials` in `rf-config.json`: `label`, `attenuation_db` and `reflection_loss_db` per band (`2.4`, `5`, `6`), `range_db` with `min`, `typical`, `max` per band (`typical` equal to `attenuation_db`), `frequency_exponent`, `confidence`, `simulation_cost`, `sources` and `notes`. Use rounded values within published ranges and say how confident you are.
2. Run `python3 tools/material_doc.py` to regenerate `docs/platform/material-database.md`. A test fails if it is out of date.
3. Run `.venv/bin/python -m pytest tests/test_rf_config_schema.py tests/test_rf_parity.py -q`. The schema test checks ordering of ranges and band references. Existing materials must keep their values.
4. The planner palette and the wall material list read the config, so no UI edit is needed. Update the family count in `tests/test_rf_config_schema.py` (`test_all_ten_material_families_present`).

## Adding a heat layer

1. Add the layer under `planner_layers.layers` in `rf-config.json`: `label`, `unit`, `lo`, `hi`, `higher_is_better` and `needs` (`null`, or `sinr` when it requires an AP with a WiFi standard). Update the schema if needed.
2. Compute the per-cell value in the layer builder in `wallhack/static/planner-heat.js` (search for `planner_layers`). Derive it from the existing analysis grid, do not run a second propagation pass.
3. Add a node-run test in `tests/test_planner_heat.py` (value at a known cell, range ends, `needs` reason when unavailable). If the layer is an estimate, say so in its `source` text and in `docs/platform/15-wifi-physics.md`.
4. Run `tools/planner_smoke.py`, which clicks every layer, and regenerate the screenshots.

## Commit style

`type: description`, lowercase, small and focused. Types: `feat`, `fix`, `perf`, `test`, `docs`, `refactor`, `chore`. Example: `feat: add omen event escalation`. One logical change per commit, tests and docs in the same commit as the code.

## Documentation and honesty rules

- Update `README.md` (verification table), `CHANGELOG.md` and the relevant file in `docs/` when you change behaviour, public routes, file structure or test steps.
- Done rows in `docs/platform/21-top-100-improvements.md` must cite files that exist (`tests/test_platform_docs.py` checks it).
- No em dashes in documents. Do not claim hardware, GPU, real-viewer or real-building results that were not measured.
- Do not commit third-party assets, secrets, API keys or large generated files. `dist/` and `data/` are generated or gitignored. Keep screenshots small (the largest full-page ones are about 1.5 MB today).
